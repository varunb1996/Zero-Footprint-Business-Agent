Conversational Business Intake Agent

Turning a messy, code-switched conversation with a small shop owner into a structured, honestly-uncertain knowledge base — and measuring whether the dialogue policy that does it actually earns its complexity.

§What this is

Most small Indian businesses — a tailor, a pharmacy, a tuition class — have no structured record of their own hours, prices, or policies. It lives in the owner's head. Building them a chatbot is pointless without that data existing somewhere queryable first, and owners won't fill out a form.

This project is an agent that interviews the owner instead — deciding, turn by turn, whether to extract a confident value, clarify an ambiguous one, or flag it uncertain rather than guess. The research question isn't whether an LLM can fill a form — it's whether an adaptive dialogue policy that clarifies selectively actually beats a naive one that just asks every question once. A thin WhatsApp Q&A layer sits on top purely to prove the resulting knowledge base is usable; it is not the contribution.

confirmed extracted with confidence inferred usable but unresolved uncertain honestly flagged, not guessed

§The dialogue policy

The core contribution lives entirely in src/agent/graph_adaptive.py, decoupled from any model via injected Extractor / Clarifier callables — the state machine's routing was proven correct with zero network calls before a real LLM was ever wired in.

Per-turn decision loop

  • High confidence → commit confirmed, move on.
  • Plausible but incomplete (e.g. "open most days, closed Sundays usually") → ask one targeted follow-up. Resolved on the second attempt → confirmed. Still unresolved after the attempt cap → uncertain.
  • No usable signal → deprioritize the field behind others still open, rather than looping on it immediately; flagged uncertain once the attempt cap is hit.

The fixed-form baseline (graph_baseline.py) shares every other line of infrastructure — same extractor, same schema, same turn-taking mechanics — but asks each field exactly once, in a fixed order, with a canned question. A "plausible" answer is committed straight to inferred; nothing is ever revisited. This is the ablation control for the turn-efficiency metric below.

Hallucination guard

The agent must never write a confirmed value it did not actually extract from owner text. This is the one rule enforced identically in both agents, and it's directly testable — see Metric 3.

§Evaluation set

20 simulated interviews were hand-authored across four categories the spec names as representative — tailor, pharmacy, small restaurant, tuition/coaching — 5 each. Every case scripts a business owner's replies for up to two attempts per field, plus a hand-written ground truth for what a correctly behaving agent should conclude, including which fields should legitimately end up uncertain because the simulated owner never gave a real answer.

Each case deliberately mixes: fields with clean, unambiguous answers; fields that are vague on the first pass and resolve on a follow-up (the adaptive agent's reason to exist); fields where the owner genuinely has no answer even after being asked twice; and Hinglish code-switching.

Coverage note: 15 of 20 cases (tailor, pharmacy, restaurant — 3 of 4 categories) completed before Groq's free-tier daily token cap was hit mid-run. The remaining 5 tuition cases are cached to resume at zero extra cost once quota resets; see Limitations.

§Finding: what the hallucination number was actually measuring

Before reporting 30%/20% as "the hallucination rate," every flagged instance was inspected individually rather than trusted at face value.

What it looked like

5 field-checks where ground truth said uncertain but the agent committed a value anyway — a 3 of 7 rate in Hinglish-labeled cases vs. 0 of 3 in English ones.

What it actually was

Only 3 vs. 7 uncertain-ground-truth instances exist at all — too small to support a language claim. And 4 of the 5 flagged cases were the extractor treating an owner's explicit "no fixed policy yet" as itself a fact worth recording, not fabrication.

pharmacy_05 · policies fieldreal trace excerpt
agent asks
What are your policies on returns, custom orders, delivery, or advance payment?
owner replies
Hum abhi soch rahe hain. ("We're still thinking about it.")
confirmed value: "No fixed policy"

Ground truth called this uncertain — no policy exists to extract. The model's read is defensible too: the owner did state something concrete. This is a disagreement in how the eval set encodes "nothing to extract," not a language-comprehension failure — and it's the same failure mode in English and Hindi alike.

Fix applied

The extraction prompt now explicitly instructs: an owner's explicit "I don't have an answer / haven't decided" is itself no usable signal, not a value — regardless of how confidently it's stated, or which language it's stated in. Live re-verification is queued behind the same quota constraint noted above.

§Metric 4 — downstream usability

The RAG layer (src/whatsapp/rag.py) is built and was verified manually rather than batch-graded: a KB seeded from a real trace answered direct-field and semantic-retrieval questions correctly, and — the important negative case — declined to answer a question about something genuinely absent from the KB instead of inventing a plausible-sounding response.

A live WhatsApp channel was deliberately not pursued: it requires a Meta developer account for zero additional research value, since the claim it exists to support — "the KB is queryable and useful" — is already demonstrated at the RAG layer directly.

§Limitations

  • Coverage: 15 of 20 planned cases evaluated (tuition category pending) — blocked by Groq's free-tier daily token cap, not a methodology gap. Cached and resumable at zero added cost.
  • Value matching: "correct" extraction is judged by normalized token overlap against hand-authored ground truth, not exact match or an LLM judge — a documented, lenient heuristic chosen to avoid roughly doubling an already-large API call volume.
  • Metric 4 is not batch-graded. The spec's ~10–15 question correct/incorrect/unanswerable pass was spot-checked, not automated.
  • Small uncertain-field sample. Only 10 ground-truth-uncertain fields exist across the 15 run cases — enough to catch the prompt bug above, not enough to make a precise hallucination-rate claim.

§Non-goals, honored

  • Not a general-purpose WhatsApp chatbot platform — that space is commoditized.
  • Not multi-tenant — one business profile per demo run.
  • No voice input — text-first, per the spec's own phasing.
  • No fine-tuning — pure prompting and orchestration throughout.
  • No exhaustive category coverage — four representative categories, generalization is explicitly future work.

§Why this scope is the right scope

This is a research prototype, not a product — deliberately. It is not wired for multiple concurrent businesses, it runs on Groq's free tier (which has a hard daily cap, not just a per-minute limit), and it talks to WhatsApp's sandbox rather than a Meta-verified Business account. None of that is a shortcoming to fix later; it's the boundary the spec draws on purpose, and the effort allocation it specifies makes the priority explicit:

ComponentSpec's stated effortThis capstone
A — Dialogue policy~60%Built, measured (Metrics 1–3)
D — Evaluation harness~15%Built, run on 15/20 cases
B — KB store~15%Built — spec calls for "intentionally simple"
C — WhatsApp / RAG demo~10%Built — spec calls for "proof of usability, not a polished product"

The 75% of effort the spec assigns to the actual research question — does an adaptive dialogue policy out-perform a naive one, and can the agent be trusted not to fabricate — is fully built and measured. The 10–15% slices are exactly the parts that would need to change for real business owners: multi-tenant storage instead of one KB per demo run, a paid LLM tier instead of a free one, a Meta-verified WhatsApp Business account instead of a sandbox. Scaling those is a known-shape engineering problem; it doesn't touch whether the dialogue policy itself is sound.

The actual claim

Metrics 1–3 are valid regardless of how many businesses run through the system. The pipeline was proven end-to-end with real data — real Groq-backed conversations, a real generated KB, real grounded RAG answers — not hypothetically. What production deployment would add is scale, not evidence.
